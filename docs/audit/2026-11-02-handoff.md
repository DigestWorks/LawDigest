## 사용자가 승인한 절차

### 0단계. 준비

1. 결정 항목 7개를 사용자와 확정한다. 감사 보고서 7절에 선택지와 권고가 있다. 리포트 탭과 가결 정의를 먼저 정한다.
2. 감사·로드맵·인수인계 문서를 main에 반영한다. 이 문서가 들어 있는 PR이 그 작업이다.
3. blocker 16건을 GitHub 이슈로 등록한다. 본문에 비밀값 위치와 값을 적지 않는다.

### 1단계부터 4단계. 묶음별 반복 절차

1. `.worktrees/` 아래에 전용 워크트리와 `{tag}/{주제}/claude` 브랜치를 만든다.
2. 대상 결함을 운영 사이트와 코드에서 다시 재현한다. 재현되지 않으면 목록에서 뺀다.
3. `ai-sdlc-workflow` 스킬로 intent → spec → plan을 쓰고 intent 수락을 받는다.
4. 수락 뒤 세 문서를 커밋하고 구현한다.
5. 바뀐 서비스의 린트, 테스트, 빌드를 실행한다.
6. 실제 화면을 데스크톱, 모바일 375px, 다크 모드로 확인한다.
7. 커밋·푸시하고 PR을 연다. 사용자가 머지한다.
8. 머지 뒤 운영 배포를 확인하고 이슈를 닫는다.
9. 워크트리와 브랜치를 정리한다.

### 5단계. 최종 확인

1. 결함 전체 목록을 체크리스트로 삼아 blocker와 major를 하나씩 운영 사이트에서 재현 확인한다.
2. blocker와 major가 0건이면 완료로 판정한다. 남은 minor는 사용자가 수용 여부를 정한다.
3. 최신 법안 발의일과 오늘의 차이가 2일 이내인지, timer가 7일 연속 성공했는지 확인한다.
4. 실제 계정으로 로그인, 30분 뒤 재요청, 스크랩, 팔로우, 알림, 탈퇴를 확인한다.
5. README 세 개와 운영 런북을 실제 상태에 맞춘다.
6. 최종 보고서에 남은 한계와 후속 작업을 적는다.

## 제약

- 다중 에이전트 재감사 워크플로를 실행하지 않는다. 비용 때문에 사용자가 금지했다. 최종 확인은 5단계 1번의 체크리스트 방식으로 한다.
- 결함 근거의 파일·라인은 `48c52a4` 기준이다. 수정 전에 현재 코드에서 위치를 다시 찾는다.
- 반박 검증이 관대했을 수 있다. 결함마다 재현 후 고친다.
- 로그인 흐름 결함은 코드 근거만 있다. 실제 계정으로 재현한다.
- 운영 DB 쓰기, 서버 timer 등록, PR 머지는 사용자 승인 뒤에만 한다.
- 웹 배포는 `deploy/` 스크립트와 `deploy/WEB_DEPLOY_ENVIRONMENTS.md`를 따른다.
